# 8. Strict Question Quality Standards

Every question must satisfy the following requirements.

### A. Clear learning objective

Each question must evaluate a specific PHP concept or engineering capability.

The tested concept must be identifiable in its metadata.

### B. Plausible answer options

All incorrect alternatives must represent realistic technical misunderstandings.

Avoid generic options such as:

- "Suppress every failure."
- "Replace the code with a comment."
- "Assume everything works automatically."
- "Check an unrelated component."
- "Remove the implementation because it is unnecessary."

Do not create answers that are obviously wrong without reading the code.

### C. No answer leakage

A candidate must not be able to identify the correct answer reliably through:

- Repeated introductory wording.
- Answer length.
- Grammatical differences.
- Unusual certainty.
- Repeated answer templates.
- A distinctive explanation style.
- Correct-answer position.

All answer options should be comparable in specificity and technical plausibility.

### D. Self-contained questions

Provide all information required to determine the correct answer.

This may include:

- PHP version.
- Initial variable values.
- Relevant class definitions.
- File contents.
- Runtime conditions.
- Database assumptions.
- Configuration.
- Expected requirements.
- Relevant error-handling behavior.

Do not require unavailable code or hidden assumptions.

### E. Accurate explanations

Every question must include:

1. The correct answer.
2. An explanation grounded in PHP behavior.
3. The relevant execution flow or technical rule.
4. A specific explanation of why each incorrect option is wrong.
5. Important edge cases or version distinctions where relevant.

Avoid generic explanations such as "The correct implementation preserves the intended guarantee."

### F. Genuine variety

Reject near-duplicates.

Changing class names, variable names, values, or filenames is not enough to create a genuinely different question.

Questions may revisit important concepts, but they must test distinct scenarios, reasoning paths or failure conditions.

# 9. Code Presentation Standards

The new PHP code viewer has already been improved and approved.

Preserve its existing visual design.

All source examples should use professional, readable formatting.

Requirements:

- Four-space indentation.
- Conventional multiline functions, methods and control structures.
- Clear nested blocks.
- Readable spacing.
- PSR-12/PER conventions where appropriate.
- Syntax highlighting.
- Proper preservation of whitespace.
- Horizontal scrolling for long lines.
- No text justification or unwanted wrapping.
- No unnecessary compression of code.

Example:

```php
class PaymentService
{
    public function process(Order $order): void
    {
        try {
            $this->charge($order);
        } catch (PaymentException $exception) {
            $this->logger->error(
                $exception->getMessage()
            );

            throw $exception;
        }
    }
}
```

Avoid writing entire classes, conditionals or exception-handling structures on one line.

Code formatting must never change PHP semantics.

Distinguish complete executable PHP files, isolated fragments, and multi-file examples.

Do not concatenate multiple PHP opening tags into an invalid single-file snippet.
