# PHP Engineer question-bank audit — 3 November 2026

The bank needs editorial and technical remediation before expansion. The most serious findings are incorrect Laravel teaching, invalid PHP snippets, predictable answer wording, and feedback leaking during exam mode. The static architecture can support the intended practice product; changing hosting or introducing Laravel is not necessary to address these findings.

This is an audit and proposal only. Existing application files, questions, IDs, and browser storage were not modified. No questions were added to the bank, no deployment was performed, and no production data was accessed. Proposed replacements in [EXAMPLES.md](EXAMPLES.md) are review drafts for existing items. The gated rollout is in [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md).

**Scope and evidence.** The user confirmed that this is intentionally a static JavaScript quiz on GitHub Pages. There is no separate Laravel application or database. Therefore migrations, Eloquent models, seeders, backend answer validation, and database examination history do not exist as implementation components here. Laravel classes and migrations inside question strings are educational examples, not an installed application.

The audited commit is `50a7a02bb29f6614ccd613dbd2703a73a3129679`. Inspection covered the repository structure, all question-building helpers, answer-length transformation, learning-note generation, the complete session/scoring/storage code, tests, and deployment workflow. Automated analysis covers all 2,500 questions; detailed content analysis focuses on the 900 Laravel/PHP questions. Manual review included all PHP lesson specifications, all Laravel roadmap specifications, all 100 curated Laravel code questions, and a systematic 75-question sample of the original 300 Laravel scenarios: positions 1, 5, and 10 in each of the 25 domains, plus targeted examples outside that sample. This is not a claim that every item has received independent semantic approval.

[evidence.json](evidence.json) contains counts, duplicate-option groups, PHP lint results, an ID/content-hash manifest for all 2,500 questions, source-file hashes, and an automated review record for each of the 900 scoped items. [probes.json](probes.json) contains executable reproductions of wording bias, exam-score leakage, shuffle mapping, selected PHP outputs, and the CSV deprecation. The scripts only read source and emit audit evidence; the PHP execution probe uses an explicit allowlist of inspected, local computation snippets.

**Implementation and data model.** `js/questions.mjs:32–80` assembles the bank. The effective question schema is `{track, topic, difficulty, prompt, options, answer, explanation, code?, roadmap?, roadmapConcepts?}`, augmented with a computed `id` and preserved `coreOptions`. There are no explicit learning objectives, runtime constraints, revision numbers, stable option identifiers, review statuses, per-option authored explanations, execution fixtures, references, or calibration results.

`question-helpers.mjs` and `code-question-helpers.mjs` always put the answer at source index zero. `roadmap-question-helpers.mjs:11` turns each lesson into four predictable question types. PHP additionally synthesizes a third lesson per domain by concatenating the two originals. This is deterministic template expansion; no model/API generation pipeline was found.

`app.js:79` shuffles options while attaching the correct flag to the corresponding option object. A probe across all 2,500 items found no answer-mapping failures. `recordAnswer` grades that flag in browser memory; it does not execute or validate PHP. This is appropriate for public practice, but results cannot serve as tamper-resistant examination credentials: the full bank and answer keys are public, and local progress is editable.

Sessions filter by track/domain/difficulty, then randomly sample without replacement. There is no balancing by objective or difficulty quota, no exclusion of sibling questions using the same lesson, no saved shuffle seed, and no durable in-progress attempt. Learn mode reveals explanations; exam mode advances immediately. Results summarize topic performance and display up to eight missed items. The “Review missed” button starts another learning session containing the missed questions.

`app.js:42–64` stores only aggregate `answered`, `correct`, `sessions`, and `best` values under `underTheHoodStats`, with a fallback read of `laravelQuizStats`. No per-question answer history or database relationships exist to migrate. Current attempts disappear on refresh/exit; the statement “Your answer is saved” means only in-memory storage until completion. Existing browser totals were not inspected or changed.

The exception-reporting and retry conclusions were checked against official [Laravel error handling](https://laravel.com/docs/13.x/errors#reporting-exceptions) and [queue retry documentation](https://laravel.com/docs/13.x/queues#time-based-attempts). Other concrete corrections and supporting sources are attached to their examples.

**Correctness and self-containment.** There is useful material worth preserving. Original scenarios cover transactions, scoped authorization, idempotency, API contracts, and production failures. LQ-089's `sync([2,4])` alternatives test actual relationship semantics. LQ-119's outbox scenario identifies a concrete crash window. The curated PHP examples for closures, comparison, short-circuiting, `match`, named arguments, traits, attributes, and fibers contain useful raw material.

Twenty-one explicitly selected, self-contained PHP snippets ran successfully on the installed PHP 8.5.2 CLI; their outputs are recorded in `probes.json`. Fifty original PHP snippets passed syntax checking; all 25 automatically combined snippets failed. Passing lint does not establish correct explanations, complete dependencies, runtime safety, or compatibility with another PHP release. Laravel examples were checked by source inspection and official framework documentation/source; no Laravel dependency installation or database execution was performed.

Self-containment must be judged against the question's demand. A conceptual code-review fragment need not define an entire framework, but it must declare every assumption that can change the answer. Exact-output questions need inputs, initial state, supporting definitions, runtime version, and diagnostic settings. Database questions need the relevant schema, constraints, engine/isolation assumptions, and initial rows when those affect the result. Framework questions need the applicable configuration, binding/authorization context, and relevant model methods. Currently these premises are inconsistent; this audit does not certify all 900 items as self-contained.

**Explanation quality.** The main source explanation is often more useful than the generated teaching notes. `buildLearningNotes` mostly restates the keyed option and a general topic guide; minimum length tests reward verbosity rather than proof. For code items, the generic “trace the displayed code” paragraph is not a worked trace. Correct explanations should identify concrete values, execution order, or a decisive constraint. Every distractor should have its own reason and, where helpful, the input or omitted condition under which it would become true. Negative-stem answers require explicit treatment as false propositions selected because the question asks for the misconception.

**Compatibility.** README targets Laravel 13 but PHP questions have no version policy. Laravel 13 requires PHP 8.3 or later and lists PHP 8.3–8.5 support; PHP 8.4 and 8.5 are suitable proposed primary validation targets, with 8.3 compatibility where claimed. These are proposed editorial targets, not a change to the deployed app. Pin exact framework/package versions in validation fixtures and record successful runtime versions per revision. Sources: [Laravel release policy](https://laravel.com/docs/13.x/releases#support-policy), [PHP supported releases](https://www.php.net/supported-versions.php).

**Quality-control limitations.** `node tests.mjs` passes. It proves counts, presence/length of content, syntactic object shape, ID uniqueness at the current ordering, source answer indexes, and full-site answer-length balancing. It does not prove PHP compilation, runtime outcomes, correct keys, plausible distractors, true concept coverage, semantic uniqueness, or exam behavior. Its source-text UI assertions do not exercise the session workflow. Requiring exactly 25 domains and uniform counts also encourages filler. Existing checks should be retained where useful, but passing them must no longer be described as semantic validation.

The recommended decision is to approve a small preservation-and-remediation phase first, then review its results before authorizing the 600-item production programme described in [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md). The audit itself makes no publication or content changes.

**Reproduction.** From the repository root, run `node tests.mjs` for the existing integrity checks. With Node and PHP available, `node audit/inspect.mjs` emits the inventory/lint evidence and `node audit/reproduce.mjs` emits the focused probes. Redirect their stdout to a new audit file if desired. Neither script writes application data or accesses browser storage. The probes are an audit harness, not a replacement for browser end-to-end tests or the proposed framework validation suite.
